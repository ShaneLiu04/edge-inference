# 工程手册：端侧上掉点、变慢、放不下、对不上，怎么查

面试官问「量化后掉点了你怎么查」「板子上慢了怎么查」，要的是**顺序**和**能区分假设的那一个观测**。每节先给可复述的结论，再给检查清单；每条都对应本仓库里一次真实的测量。数据中心侧（时间线空洞、NCCL 挂住、显存碎片）见 [mlsys-infra ENGINEERING](https://gitee.com/liu-xingyan04/mlsys-infra/blob/main/interview/ENGINEERING.md)。

## 1. 量化后掉点

**结论：先二分「权重还是激活」，再逐点定位，最后才换校准方法或上 QAT。**

1. **只量化权重（激活保持 fp32）**。W8 不掉点、W4 掉点，说明问题在权重粒度：本仓库 W4 per-tensor 76.4%、per-channel 83.2%，fp32 88.2%。
2. **只量化激活（权重保持 fp32）**。掉点就逐个量化点打开，一次只量化一个点，看哪一个点单独就能让精度下降（`lab2-quantization` 的 `localize` 步骤）。
3. **看那个点的范围**。把校准器选出的 [lo, hi] 和 MSE 校准的范围放在一起比。本仓库的 KL 校准在每个 ReLU6 输出上选出的阈值中位数只有 MSE 阈值的 0.27 倍（去掉精确零后 0.73 倍），单点最多掉 7.0 个百分点，合起来 W8A8 只剩 63.7%。
4. **找出原因再改**：KL 的问题是零值尖峰主导散度，排除精确零值（`calib_kl_nonzero`）就恢复；不是「KL 不好，换 percentile」。
5. **混合精度按敏感度排序，不按大小**：W4 基线 83.0%，按敏感度把 4 层提回 W8（+4.3 KiB）到 87.1%；按参数量提最大的 4 层（+54 KiB）只到 83.6%。

| 看到的 | 最可能的原因 | 区分它的观测 |
| --- | --- | --- |
| W8 per-tensor 掉点，per-channel 不掉 | BN 折叠后通道幅值差两个数量级 | 按通道看权重相对误差，有通道接近 100%（被量化成 0） |
| A8 掉点，A16 不掉 | 某个点的范围被截得太狠或太松 | 单点量化定位；该点校准范围与 minmax/MSE 对比 |
| 校准样本从 512 换到 8 结果几乎不变 | 校准对样本数不敏感，问题不在样本 | `calib_size` 步骤：minmax/MSE 的 A6 精度在 8 到 2048 张之间变化不到 0.15 个点 |
| PTQ 上掉 5 个点，QAT 回来 | 权重量化误差可被训练吸收 | QAT 第 0 个 epoch 与最终精度的差 |
| PyTorch 伪量化不掉点，ONNX Runtime 掉 | 导出后的量化点位置或融合与模拟不一致 | 对比两边的 QDQ 节点位置；BN 是否在导出前折叠 |

## 2. 两个运行时的整数结果对不上

**结论：先确认差 1 的比例和位置，再查舍入语义。差 1 不是 bug，差很多才是。**

1. **算差异分布**：差值是否只有 ±1、比例多大。本仓库 TFLite 式两次舍入与 ORT 对比，正常数据上 99.93%–99.97% 相等，最大差 1。
2. **构造平局**：让累加值恰好落在 .5 上。ORT 的 QLinearConv 在平局上与 fp32 乘 + round-half-even 100% 一致；与「平局远离零」的 double 实现只有 99.47%–99.78% 一致。
3. **看 shift**：两次舍入出错概率约 2^−(shift+1)。乘数 M 越小（shift 越大）越少见；M≈0.4 时 25% 的输出差 1。
4. **查饱和**：在 x86 上用 `vpmaddubsw` 的实现，权重超过 ±64 时 int16 中间和饱和。wmax=100 时 99% 的输出错，最差误差 43,326，这不是舍入问题。

| 看到的 | 最可能的原因 | 区分它的观测 |
| --- | --- | --- |
| 0.03%–0.1% 的输出差 1 | 两次舍入（SRDHM + RoundingDivideByPOT）vs 一次舍入 | 差 1 的比例与 2^−(shift+1) 吻合；一次舍入（`TFLITE_SINGLE_ROUNDING`）后降到 0–2e-4 |
| 只有平局处差 1 | round-half-even vs round-half-away vs 向 +∞ | 构造 .5 平局的测试集，差值全部集中在平局 |
| 大量输出差很多 | int16 饱和、zero-point 没减、padding 填 0 而不是 zx | 把权重限制在 ±64 后是否消失；padding 区域单独比较 |

## 3. 端侧变慢

**结论：先算这一层的上界，再看实测离上界多远；离得远才看 kernel。**

1. **先算强度和上界**（[公式卡](FORMULAS.md) E1–E3）。本机 `host-roofline` 给出 L1、L2、DRAM 各级带宽和 fp32、int8 两条算力屋顶，每一层卷积都能放到图上。
2. **看是否打到了该层的屋顶**：depthwise、GEMV 落在带宽屋顶下，优化方向是减少字节（int8、块量化、融合），不是更多 SIMD。
3. **看 epilogue**：int8 GEMM 的 requant 如果是标量写的，打包 GEMM 从 129 掉到 20 GOP/s；融合进寄存器后 66，融合比标量 epilogue 快 1.2–3.5 倍（int8-kernels 实验）。
4. **看布局**：同一条 VNNI 指令，权重按 [N/16][K/4][16][4] 打包与按行点积的吞吐差 2.0–30.8 倍，差别在于每条指令能复用多少次已加载的激活。
5. **最后才调 tile 和线程数**；有调度搜索时，用代价模型筛候选，真机只测 top-k。

## 4. 内存放不下

**结论：先报下界（存活峰值），再报规划器离下界多远，最后才改执行方式或模型。**

1. **算存活峰值**：MBv2-1.0@224 int8 是 1,505,280 B，规划器（按大小贪心）已经贴住；first-fit 多 13.3%，换规划器就能省。
2. **找峰值在哪一层**：MobileNetV2 在第二个 block（expand 输出 + stride-2 depthwise 输出）。
3. **原地 depthwise**：峰值移到 expand 处，省 6.7%。省多少取决于第二高点，单层省的不等于整网省的。
4. **按 patch 推理**：前 4 个 block 切 2×2，峰值降到 566,784 B，整网 MACs +7.7%；继续切不再降，因为峰值已移到 cut 之后。
5. **换模型**：在 nRF52840（256 KB）上，MBv2-0.35@160 下界 375 KiB 放不下，cut=4、3×3 patch 降到 100 KiB，整网 MACs +27%。

## 5. 结果怎么证明

1. **找一个逐位相等的恒等式**：C++ int8 卷积与 NumPy int64 参考逐位相等；SIMD requant 与标量 requant 逐位相等；Q4_0 打包与 `gguf.quants` 逐字节相等。本仓库每个实验都有这类测试。
2. **找一个闭式**：双缓冲事件模拟与 n·max + min 在随机参数上相等；Winograd 在 fp64 下与直接卷积相等，误差只在低精度下出现。
3. **数字从文件来**：README 里的每个数在 `claims.json` 里有一条，`scripts/check_claims.py` 对照 `artifacts/raw/` 校验。
4. **报分布不报单点**：计时报 p50 和 p10/p90，精度报多个种子的均值和标准差（`calib_size` 每档 3 个种子）。
